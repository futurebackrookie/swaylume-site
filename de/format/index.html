01Aufbau

Einen zu bauen ist einfacher, als du denkst.

Ein .swaylume ist einfach ein Ordner — macOS registriert ihn als Bundle, deshalb zeigt der Finder eine einzelne Datei. Darin: ein Manifest, das sagt was das ist, und ein content/ mit dem Material. Mehr nicht. Kein Build-Schritt, kein SDK, keine Registrierung.

Ein Manifest, ein Ordner.

preview.jpg ist optional — ohne sie sucht Swaylume selbst ein Titelbild aus dem Material (bei Video werden schwarze Bilder übersprungen und das Bild mit der größten Helligkeitsvarianz genommen). Was in content/ liegt, hängt von type ab.

MyWallpaper.swaylume/ ├── manifest.json // 必需 / required ├── preview.jpg // 可选 / optional └── content/ // 必需 / required ├── video.mp4 // type == "video" ├── index.html + assets/ // type == "web" ├── image.png // type == "image" └── layers.json + *.png // type == "layered"
02Manifest

Was in manifest.json gehört.

Vier Pflichtfelder, der Rest ist optional. Die Lesende Seite ignoriert unbekannte Felder — Zusätzliches ist also nie ein Fehler.

{ "formatVersion": 1, "title": "Neon City", "author": "someone", "type": "video", "entry": "video.mp4", "preview": "preview.jpg", "fillMode": "fill", "muted": true }
FeldPflichtHinweise
formatVersionPflichtDerzeit immer 1. Neuere Pakete als unterstützt lehnt die App ab
titlePflichtAnzeigename
typePflichtvideo / web / image / layered
entryPflichtEinstiegsdatei, relativ zu content/
authorUrheberangabeErscheint in Bibliothek und Eigenschaften
previewVorschaubild, relativ zur Paketwurzel
fillModefill / fit / stretch / centerStandard: fill
mutedStandard trueNur für Material mit Ton relevant
propertiesEinstellbare ParameterNur für web-Hintergründe, siehe unten
sourceNoteHerkunftsnotizNur Anzeige, ohne Wirkung auf die Logik
03Parameter

Lass andere deinen Hintergrund in den Eigenschaften einstellen.

Nur für web-Hintergründe. Was du im Manifest deklarierst, taucht genau so in Swaylumes Eigenschaftenpalette auf — Schalter, Regler, Farben, Dateiauswahl, Textfelder. Die Werte erreichen die Seite beim Ziehen, ganz ohne Neuladen.

"properties": { "speed": { "number": { "_0": { "value": 0.35, "min": 0, "max": 1 } } }, "showtext": { "bool": { "_0": true } }, "greeting": { "text": { "_0": "hello" } }, "schemecolor": { "color": { "_0": "0.2 0.6 1" } }, "background": { "file": { "_0": { "fileType": "image" } } } }
caseTyp von _0Darstellung
boolBoolSchalter
number{ value, min, max }Regler
textStringTextfeld
colorString, "r g b" — drei Fließkommazahlen 0…1Farbwähler
file{ fileType }Dateiauswahl
directory{ fileType }Ordnerauswahl
Bei number ist _0 ein Objekt, keine nackte Zahl. Ein Regler lässt sich ohne seinen Bereich nicht zeichnen — Wallpaper-Engine-Regler kommen in freier Wildbahn als 0…1, 0…100, 0…359, 0…1000 vor. Ohne Bereich muss die Palette raten, und jedes Ziehen landet falsch.
Bei file / directory schreibst du nur fileType. Sobald jemand in Swaylume etwas auswählt, ergänzt die App bookmark und displayName — ein security-scoped Bookmark, das nur in der lokalen Bibliothek liegt, nicht Teil des Paketformats ist und beim Export entfernt wird (es trägt deine Ordnernamen nach außen).
Seiten, die für Wallpaper Engine geschrieben wurden, laufen meist unverändert. Die Werte erreichen die Seite als { name: { value, type } } über wallpaperPropertyListener.applyUserProperties — dieselbe Vereinbarung wie bei Wallpaper Engine. Property-Listener, zufällige Dateiauswahl und Audio-Callbacks ergänzt die Kompatibilitätsschicht.
04Ebenen

2.5D-Parallaxe: ein paar Bilder, jedes mit einer Tiefe.

Setze type auf layered und lege eine layers.json plus deine freigestellten Bilder in content/. depth läuft von 0…1: 0 ist am weitesten weg und bewegt sich kaum, 1 ist am nächsten und folgt dem Zeiger am stärksten. Die Relativbewegung zwischen den Ebenen erzeugt die Tiefe — ohne Videodekodierung und mit kaum messbarem Verbrauch.

// Die komplette Formatdefinition eines Ebenen-Hintergrunds { "layers": [ { "image": "sky.png", "depth": 0.0 }, // am weitesten weg, bewegt sich kaum { "image": "hills.png", "depth": 0.45 }, { "image": "tree.png", "depth": 1.0 } // am nächsten, bewegt sich am meisten ] }
05Zusage

Wie sich dieses Format ändern darf.

Nur eine brechende Änderung fasst formatVersion an. Anders gesagt: ein Paket, das du heute baust, hört nicht auf zu funktionieren, weil wir morgen ein Feld ergänzen.

Neue Felder sind immer optional.Die lesende Seite muss unbekannte Felder ignorieren statt zu scheitern. Das ist eine harte Regel, kein Ratschlag.
formatVersion steigt nur bei brechenden Änderungen.Ein Feld zu ergänzen bricht nichts. Sollte sie doch steigen, laden alte Pakete weiter — ihnen fehlt nur das Neue.
Die alte Endung gilt weiter.Vor der Umbenennung als .livewall exportierte Pakete tragen innen dasselbe v1-Format; Finder-Zuordnung und Import funktionieren wie bisher. Nur neue Exporte heißen .swaylume.
Schreiber und Leser sind ein Vertrag.Konverter und Importpfad der App ändern sich gemeinsam. Läuft eine Seite vor, exportierst du Pakete, die du selbst nicht mehr lesen kannst.
Lass es vor dem Einreichen lokal laufen. Zieh das .swaylume direkt in Swaylume: Es sollte abspielen, und jeder Parameter in den Eigenschaften sollte tun, was du gemeint hast. Die CI des Katalog-Repos prüft Struktur und Prüfsummen erneut — ob es richtig aussieht, kann sie nicht prüfen. Das kannst nur du.

01Layout

Making one is simpler than you think.

A .swaylume is just a folder — macOS registers it as a bundle, so Finder shows it as a single file. Inside: one manifest saying what this is, and a content/ folder with the material. That’s it. No build step, no SDK, no account to register.

One manifest, one folder.

preview.jpg is optional — leave it out and Swaylume picks a cover frame from the material itself (for video it skips black frames and takes the one with the most going on). What goes in content/ depends on type.

MyWallpaper.swaylume/ ├── manifest.json // 必需 / required ├── preview.jpg // 可选 / optional └── content/ // 必需 / required ├── video.mp4 // type == "video" ├── index.html + assets/ // type == "web" ├── image.png // type == "image" └── layers.json + *.png // type == "layered"
02Manifest

What goes in manifest.json.

Four required fields, everything else optional. The reader ignores fields it doesn’t recognise, so extras are never an error.

{ "formatVersion": 1, "title": "Neon City", "author": "someone", "type": "video", "entry": "video.mp4", "preview": "preview.jpg", "fillMode": "fill", "muted": true }
FieldRequiredNotes
formatVersionRequiredAlways 1 for now. The app refuses packages newer than it supports
titleRequiredDisplay name
typeRequiredvideo / web / image / layered
entryRequiredEntry file, relative to content/
authorCreditShown in the library and the inspector
previewPreview image, relative to the package root
fillModefill / fit / stretch / centerDefaults to fill
mutedDefaults to trueOnly meaningful for material with audio
propertiesUser-adjustable parametersOnly used by web wallpapers — see below
sourceNoteProvenance noteDisplay only, no logic depends on it
03Parameters

Let people tune your wallpaper from the inspector.

Web wallpapers only. Whatever you declare in the manifest is what shows up in Swaylume’s inspector — switches, sliders, colours, file pickers, text fields. Values reach the page the moment the user drags, with no reload.

"properties": { "speed": { "number": { "_0": { "value": 0.35, "min": 0, "max": 1 } } }, "showtext": { "bool": { "_0": true } }, "greeting": { "text": { "_0": "hello" } }, "schemecolor": { "color": { "_0": "0.2 0.6 1" } }, "background": { "file": { "_0": { "fileType": "image" } } } }
caseType of _0How it appears
boolBoolSwitch
number{ value, min, max }Slider
textStringText field
colorString, "r g b" — three 0…1 floatsColour picker
file{ fileType }File picker
directory{ fileType }Folder picker
number takes an object for _0, not a bare value. A slider can’t be drawn without knowing its range — Wallpaper Engine sliders show up as 0…1, 0…100, 0…359, 0…1000 in the wild. Without the range the inspector has to guess, and every drag lands in the wrong place.
For file / directory you only write fileType. Once the user picks something in Swaylume, the app fills in bookmark and displayName — that’s a security-scoped bookmark, it lives only in the local library file, it is not part of the package format, and export strips it (it carries your folder names, which shouldn’t travel).
Pages written for Wallpaper Engine mostly work unchanged. These values reach the page as { name: { value, type } } through wallpaperPropertyListener.applyUserProperties, matching Wallpaper Engine’s contract. Property listeners, random file picking and audio callbacks are filled in by the compatibility layer.
04Layered

2.5D parallax: a few images, each with a depth.

Set type to layered and put a layers.json plus your cut-out images in content/. depth runs 0…1: 0 is farthest and barely moves, 1 is nearest and tracks the pointer most. The relative motion between layers is where the depth comes from — no video decoding, almost no power draw.

// The entire format definition for a layered wallpaper { "layers": [ { "image": "sky.png", "depth": 0.0 }, // farthest, barely moves { "image": "hills.png", "depth": 0.45 }, { "image": "tree.png", "depth": 1.0 } // nearest, moves most ] }
05Contract

How this format is allowed to change.

Only a breaking change touches formatVersion. Put differently: a package you build today won’t stop working because we added a field tomorrow.

New fields are always optional.The reader must ignore fields it doesn’t recognise rather than fail. That’s a hard rule, not advice.
formatVersion only rises on a breaking change.Adding a field isn’t breaking. If it ever does rise, old packages still load — they just miss the new capability.
The old extension still works.Packages exported as .livewall before the rename hold the same v1 format inside; Finder association and import both still work. Only new exports use .swaylume.
Writer and reader are one contract.The converter and the app’s import path change together. Letting one side move first means exporting packages you can’t read back.
Run it locally before you submit. Drag the .swaylume straight into Swaylume: it should play, and every parameter in the inspector should do what you meant. The catalog repo’s CI re-checks structure and checksums, but it cannot check whether the thing looks right — only you can.
